## Authentication

Three transports, any one of them works:

```http
Authorization: Bearer <token>
X-Gotify-Key: <token>
?token=<token>
```

`?token=` is accepted on HTTP endpoints too (`extractToken` reads all three sources), but headers
are preferred.

Token types:

| Token | Format | Notes |
|---|---|---|
| Master key (`AUTH_TOKEN` / `AUTH_TOKEN_FILE` / generated by first-run setup) | `cz.` + 30 base62 chars (33 total) | Super-admin identity; also keeps old Gotify clients working. **Resolution order: `AUTH_TOKEN` plaintext → file pointed at by `AUTH_TOKEN_FILE` → `meta.auth_token` in the DB → *uninitialized*** (a brand-new instance only has one after the setup page completes). Whichever source wins, the effective value is written back into `meta.auth_token` on every boot |
| Device token issued at login | same format | Bound to **the account that logged in** (super-admins included) |
| User device token | `cz.` + 30 base62 chars (33 total) | Created at registration. Unified into this format on 2026-09-30 |

> Both credential kinds share one format. The `cz.` prefix is only a **readability marker** (you
> can tell a Chatz credential at a glance) — it is **not a security boundary**. A device token is
> authenticated by exact whole-string match against the `devices` table (`auth.js:resolveToken`);
> the master key is compared as a whole string against `AUTH_TOKEN`. Forging the prefix buys you
> neither.
>
> ⚠️ There was a **breaking migration on 2026-09-30** (two independent markers):
> - `device_token_cz_v2`: all existing 64-char hex **device tokens** were re-issued as `cz.`;
> - `auth_token_cz_v2`: the **master key** also moved to `cz.`.
>
> **Exception for the master key**: if `AUTH_TOKEN` comes from the environment or a file (both
> rank above the database), the migration **does not touch it** — the env value would just
> override it again, and all that would produce is a harder-to-debug "meta disagrees with what is
> actually in effect" state. Change it yourself in `.env`. After changing it, every holder (admin
> password logins, pasted-token logins, old Gotify clients) must pick up the new value.

> When the master key matches, the identity resolves to **the first user in the DB with
> `is_admin = 1`**, flagged `isLegacyAuth = true` (there is no device id, so `POST /auth/logout`
> is a no-op for it).

Permission levels:

| Level | Meaning |
|---|---|
| **Public** | No token required |
| **Logged in** | Any valid token |
| **Admin** | `role = 1` — manages **their own** apps and routing rules; cannot manage channels and cannot see other people's apps/rules |
| **Super-admin** | `role = 2` |
| **Creator / super-admin** | The channel's creator, or a super-admin |
| **Channel subscriber / super-admin** | Subscribed to the channel, or a super-admin |

> ⚠️ Since 2026-10-01: **apps and routing rules are isolated per user**. Every logged-in user
> manages their own set; admins no longer have global reach (they only see their own).
> The super-admin's "omniscience" was **also pulled back from the everyday endpoints** —
> `GET /channel`, `GET /message` etc. are all subscription-scoped. Site-wide data now lives in
> [section 15](#15-super-admin-pages-site-wide-read-only).
>
> 📌 Note on role 1: `requireAdmin` still exists in `src/auth.js` but **has no call sites left** —
> every privileged endpoint uses `requireSuper`. In practice role 1 behaves almost exactly like
> role 0, and the web UI no longer offers it in the role dropdown (existing role-1 accounts keep
> their role until changed). Anything that needs "can see everything" must test `isSuper`.

## Conventions

### Error responses

Errors are always JSON:

```json
{"error": "description"}
```

| Status | Meaning |
|---|---|
| 400 | Bad argument |
| 401 | Token missing or invalid |
| 403 | Insufficient permission |
| 404 | Not found |
| 409 | Conflict (username / email already taken — channel names may duplicate, so no longer 409) |
| 429 | Rate limited (response carries `Retry-After`) |
| 500 | Internal server error |

Examples:

```json
{"error": "Not logged in or session expired", "errorCode": 401}
{"error": "Admin permission required"}
{"error": "Super-admin permission required"}
{"error": "Too many requests, please try again later", "retryAfter": 37}
```

**Role-based violations are audited** (`auth.forbidden` / `auth.forbidden_super`, throttled to one
entry per *user + path* per 5 minutes), so if someone keeps probing admin endpoints with an
ordinary account, you will find traces in `GET /audit`. (Business-level denials such as "accessing
a channel you are not subscribed to" return 403 *without* an audit entry, to keep normal mis-clicks
from generating noise.)

Unmatched routes return `404 {"error": "Not found"}`.

### Rate limits

Counters live in memory and **reset on restart**.

The client IP used for counting is resolved centrally by `clientIp.js`, with exactly the same rules
as the audit log: **only the TCP peer address by default**; `X-Forwarded-For` is trusted only if
`TRUST_PROXY` is explicitly configured (see the "client IP" chapter in README / DEPLOY).

⚠️ **Every limit has its own counter** (keys look like `password:192.168.2.5`) — normal API traffic
does not eat into the registration / password-change budget. If an endpoint returns 429 on its very
first call, verify that you really are calling too often; do not assume another traffic source
crowded you out (that bug was fixed on 2026-09-29).

| Endpoint | Dimension | Limit |
|---|---|---|
| Global fallback | per IP | 600 / 60 s |
| `POST /hook/:token` | per app token | 60 / 60 s |
| `POST /hook/preview` | per IP | 30 / 60 s |
| `POST /attachment` | per user | **10** / 60 s (lowered from 30 on 2026-09-30, alongside the quota) |
| `POST /route/test` | per IP | 20 / 60 s |
| `POST /channel` | per IP | 20 / 1 h |
| `POST /application` | per IP | 30 / 1 h (any user can create apps since 2026-10-01; previously admin-only and unlimited) |
| `POST /route` | per IP | 30 / 1 h (same) |
| `POST /device` | per IP | 20 / 1 h |
| `POST /device/rotate` | per IP | 20 / 1 h |
| `POST /auth/register` | per IP | 3 / 1 h |
| `POST /auth/login` | per IP | 30 / 5 min |
| `POST /auth/login` | per IP + username | 5 / 5 min |
| `POST /setup` | per IP | 20 / 1 h |
| `POST /auth/forgot-password` | per IP | 10 / 1 h |
| `POST /auth/reset-password` | per IP | 20 / 10 min |
| `PATCH /user/password` | per IP | 10 / 10 min |
| `PATCH /user/username` | per IP | 10 / 10 min |
| WebSocket connections | global / per user | 1000 total / 10 per user |

Those 18 rows correspond to **18 `rateLimit({ name })` call sites** (16 in `src/*.js` plus 2
login-specific ones inside `rateLimit.js`), checked one by one. The last row is not this mechanism
at all — it is the connection cap in `ws.js`.

(Note added 2026-09-30: when `route_test` / `channel_create` / `device_create` were added, this
table was nearly forgotten — which is precisely why the table exists. **Changing a threshold also
means coming back here**, not just adding new rows.)

(Note added 2026-10-01: it was **missed again** when `device_rotate` was added; only noticed while
adding `app_create` / `route_create`, and then filled in. Same trap, twice — next time you touch
rate limiting, diff `grep -rn "rateLimit({" src/` against this table line by line instead of
trusting memory.)

**Add a row here whenever you add a limiter** — each one carries a `name` and counts separately, so
forgetting produces no error whatsoever.

`429` responses carry `Retry-After` (seconds) and a `retryAfter` field:

```json
{"error": "Too many requests, please try again later", "retryAfter": 512}
```

### Request body size limits

Anything larger returns `413` (handled by Express's raw / json parsers).

| Path | Limit |
|---|---|
| `/hook`, `/certs` | 1 MB |
| `/application/:id/icon`, `/channel/:id/icon`, `/user/avatar` | 5 MB |
| `/background` | 8 MB |
| `/attachment` | 20 MB (raw layer) / **8 MB** (business layer, see below) |
| All other JSON endpoints | 1 MB |

> Binary uploads (icons, avatars, background, attachments, certificates) all go through
> `express.raw` — the body is **raw bytes**, not a JSON field.
>
> ⚠️ **Attachments have two layers of limits**: the `express.raw` layer is 20 MB (anything bigger
> is rejected by the parser and never reaches business logic), and the business layer has
> `ATTACHMENT_MAX_FILE_MB` (default 8 MB). The stricter of the two wins.
> Attachments additionally have a **total quota**, `ATTACHMENT_MAX_TOTAL_MB` (default 500 MB);
> exceeding it returns `507` (distinct from `413`) — see `src/attachments.js`.

### Image type detection

Uploaded images always get their extension re-derived from the **file magic number**; the client's
`Content-Type` or filename is ignored. Only `png / jpg / gif / webp / svg` are recognised.

- Avatars and backgrounds **additionally reject `svg`** (they are rendered inline, and SVG is a
  script carrier)
- Attachments whose extension lands on the blacklist (`html / svg / js / xml …`) are forced to
  `.bin`

## 1. Basics

### `GET /health` public

```json
{"ok": true, "online": 3, "https": true, "ts": 1789982992010}
```

| Field | Meaning |
|---|---|
| ok | Whether the service is healthy |
| online | Current WebSocket connection count |
| https | Whether HTTPS is enabled |
| ts | Current timestamp |

### `GET /config` public

Runtime config the web client fetches before starting up.

```json
{"certsUiEnabled": true, "httpsPort": 20443, "aggWindowMs": 300000, "aggMaxLifetimeMs": 1800000, "lang": "zh", "langLocked": false}
```

| Field | Meaning |
|---|---|
| certsUiEnabled | Whether to show the "HTTPS certificates" panel in the web UI (turn off with `CERTS_UI_ENABLED=false`) |
| httpsPort | Current HTTPS port |
| aggWindowMs | Rolling aggregation window (`AGG_WINDOW_MS`); more time than this since the **last fold** starts a new message |
| aggMaxLifetimeMs | Maximum lifetime of a single aggregated message (`AGG_MAX_LIFETIME_MS`), measured from **message creation**; `0` = unlimited |
| lang | Language the **server log** currently speaks: `zh` / `en` |
| langLocked | `true` = the `LOG_LANG` environment variable pinned it and the web UI cannot move it |

### `GET /config/lang` logged in

```json
{ "lang": "zh", "locked": false }
```

The log language currently in effect, plus whether `LOG_LANG` has locked it.

### `PUT /config/lang` super-admin

Changes the **log** language for the whole instance. Takes effect **immediately** — no restart.

```json
// request
{ "lang": "en" }
```

- Only `en` / `zh` are accepted; anything else is treated as `zh`
- Ordinary users and admins get `403` (registration is fully open — otherwise anyone who signs up
  could decide what language your logs speak)
- When `LOG_LANG` is set the endpoint still returns `200`, but the effective value does not change
  (`locked: true`)
- Switching writes a `🌐 log language switched to English` line to the log and records a
  `config.set_lang` audit row

```json
// response (when locked=true, `lang` may differ from the request)
{ "lang": "en", "locked": false }
```

> 💡 The language button in the web UI sidebar calls this endpoint in passing, so **switching the UI
> to English switches the container log too**. The setup page is the one moment where no super-admin
> exists yet but the language still gets decided — `POST /setup` carries `lang`.

### `GET /version` logged in

```json
{"version": "2.0.0", "commit": "local", "buildDate": "2026-09-21T09:29:52.019Z"}
```

`buildDate` is **the moment the endpoint was called**, not the build time.

## 2. Users & devices

### `GET /setup/status` public

Used by **first-run setup** on a fresh install. It triggers on `meta.setup_completed = '0'`, which
`migrate.js` writes when it creates the `admin` user; existing deployments get backfilled to `'1'`
during migration, so upgraded instances are never bounced into the setup page.

```json
// response
{ "needsSetup": true }
```

A single boolean — nothing about the instance's internals is leaked.

### `POST /setup` public (limited to 20 / hour / IP)

Sets up the admin account for a fresh install. **Succeeds at most once in the instance's lifetime**;
every later call returns `403`.

```json
// request
{
  "username": "admin",
  "password": "use your own password",
  "displayName": "Admin",
  "lang": "zh"
}
```

Constraints:

- `username` 2–32 chars, only `a-z A-Z 0-9 _ - .`; colliding with another user → `409`
- `password` **6–128** chars (same as ordinary registration — admins get no extra strictness)
- `lang` optional, `en` / `zh`; only those two literals are honoured, anything else is ignored. It
  decides what language the **server log** speaks (stored in `meta.lang`) and is the one moment
  where no super-admin exists yet but the language still gets decided. It also renames the
  pre-seeded "Default channel" to match — the front-end i18n never touches channel names
  (that is user data)
- `email` optional, used by "forgot password"; malformed → `400`, already taken → `409`
- setup already completed → `403`

On success it:

1. Takes over the `admin` user pre-created by `migrate.js` — it **renames and re-passwords that
   user, it does not create a second admin**, so you never end up with two admins and the default
   channel subscription it already holds survives
2. Sets `meta.setup_completed` to `'1'`, closing the endpoint
3. If `lang` is `en` / `zh`, writes it to `meta.lang` — the container log follows it from then on.
   When the language actually changes it logs `🌐 log language switched to English` **in the new
   language**, so you can confirm it without restarting
4. **Renames the pre-seeded "Default channel"** to match (`默认频道` ⇄ `Default channel`).
   🔴 Only if its name is still the seeded original — a channel the user renamed is never
   overwritten by a language switch
5. Generates and returns the master key, so the setup page can enter the app without a second login

> ⚠️ The master key is **generated at this step** (changed 2026-10-05); before it, no master key
> exists at all and none is ever written to the container log. What comes back is the master key
> itself (`cz.` + 30 chars), registered afterwards as a device named "default Token" — so the
> super-admin holds exactly one credential and never wonders which of two is valid.

> Also: a successful `POST /auth/login` sets that flag to `'1'` as well. Somebody getting in with
> real credentials means the instance is already being managed and should not show setup again.
>
> ⚠️ Completing setup does **not** revoke the old `AUTH_TOKEN` — Gotify clients are still using it.
> To revoke, delete the matching row under "Account → Security & sign-in → Signed-in devices".

### `POST /auth/register` public

Request:

```json
{
  "username": "alice",
  "password": "alice123",
  "displayName": "Alice",
  "email": "alice@example.com"
}
```

Response:

```json
{
  "user": {
    "id": 2,
    "username": "alice",
    "displayName": "Alice",
    "avatar": null,
    "isAdmin": false,
    "createdAt": 1789968398982
  },
  "token": "cz.xxxxxxxxxxxxxxxxxxxxxxxxxxxxxx"
}
```

> Device tokens are always `cz.` + 30 base62 chars (33 total). Do not confuse them with the 10-char
> **app** token — that one is embedded in webhook URLs (see [5. Applications](#5-applications)).

Constraints:

- `username` 2–32 chars, only `a-z A-Z 0-9 _ - .`
- `password` ≥ 6 chars
- `email` is **optional**: if provided it must be valid and must not already belong to another
  account (duplicate → `409`); it is what "forgot password" uses to locate the account, so accounts
  without an email cannot use password reset
- username taken → `409`
- Registration produces an **ordinary user**. ⚠️ The old claim in earlier docs that "when the system
  has no admin yet, the first user to register becomes admin" is **not true in this version**:
  `migrate.js` pre-creates `admin` at boot, so `users` is never empty. The real ways to get admin
  are the **first-run setup page** (above) on a fresh install, or logging in with `AUTH_TOKEN` and
  managing roles yourself.
- A device token named `Web` is created automatically

> ⚠️ **Registration does not auto-subscribe to any public channel.** A new account's drawer is
> empty; it must explicitly subscribe via "Discover channels". The only exception: the creator of a
> channel is auto-subscribed to it.

### `POST /auth/login` public

```json
// request
{
  "username": "alice",
  "password": "alice123",
  "deviceName": "Phone"
}

// response: same shape as register
```

- **All users** (admins and super-admins included): login issues **their own** device token, so the
  token you get back always corresponds to the account that logged in
- **One user = one login token**: the lowest-id token for that user is reused (excluding the global
  master key) and only `last_seen` is updated; a new one is issued only if none exists. So repeated
  logins (including incognito or after clearing localStorage) and logging in from another device all
  return **the same token**. Want an extra one? Use "Add device", `POST /device`.

> ⚠️ Before 2026-10-01, "admin login returns the global `AUTH_TOKEN` (master key)". But the master
> key is the "Default token" row in `devices`, bound to the **first** admin — so a second admin
> logging in received the master key, became the first person identity-wise, and got super-admin
> rights for free (symptom: "bob promoted to admin, logs in, and is actually yezi"). Now the
> logged-in user's own token is always issued.

Unknown username and wrong password both return `401 {"error": "用户名或密码错误"}` (that Chinese string is
the literal server message; it is not translated). The same response is used for both cases,
deliberately, to prevent username enumeration.

### `POST /auth/forgot-password` public (limited to 10 / hour / IP)

```json
// request
{"email": "alice@example.com"}

// response (identical whether or not the mailbox is registered — no information leak)
{"ok": true, "message": "If that email is registered, a reset link has been written to the service log; the admin can read it with docker compose logs"}
```

There is no SMTP integration, so the reset link is **printed to the container log**
(`docker compose logs chatz`):

```text
📧 Password reset requested
   User: alice <alice@example.com>
   Link: http://<host>/reset-password?token=xxxx...
   Valid: 30 minutes (single use)
```

- Only the sha256 hash of the token is stored, never the plaintext; expires in 30 minutes; dies
  after one use
- Any password change by any route invalidates every unused reset link for that user

### `GET /auth/reset-password/validate` public

```json
// request: ?token=xxx
// response
{"valid": true, "reason": null}          // valid
{"valid": false, "reason": "expired"}    // expired
{"valid": false, "reason": "used"}       // already used
{"valid": false, "reason": "invalid"}    // invalid
```

### `POST /auth/reset-password` public (limited to 20 / 10 min / IP)

```json
// request
{"token": "xxx", "password": "newpassword123"}

// response
{"ok": true}
```

Constraints: `password` 6–128 chars; invalid / used / expired token → `400`.

### `GET /auth/me` logged in

```json
{
  "id": 2,
  "username": "alice",
  "displayName": "Alice",
  "avatar": "/user-avatars/user-2-1789.jpg",
  "isAdmin": false,
  "createdAt": 1789968398982

```

### `POST /auth/logout` logged in

Deletes the token of **the current device** (the device id is looked up from the token).

```json
{"ok": true}
```

When called with `AUTH_TOKEN` there is no device id, so the endpoint returns `ok` but deletes
nothing.

> **Admin exception**: an admin logging in with a password reuses the global `AUTH_TOKEN`, which
> maps to the "Default token" row in `devices`. Logging out does **not** delete that row; the
> response gains `{"ok": true, "keptDefaultToken": true}`.
> Why: deleting it is pointless — `AUTH_TOKEN` goes through the "not found in `devices`, compare
> against the global token" fallback, so it keeps working with the row gone; and the next password
> login would recreate it anyway. To actually retire that master key you must change `AUTH_TOKEN`
> itself (in `.env` / `meta`).

### `GET /device` logged in

Returns all devices of the current user, **but no plaintext for any row** — only an 8-char
fingerprint.

```json
[
  {
    "id": 1,
    "name": "Default token",
    "token": null,
    "tokenPreview": "kR9mX2pQ",
    "tokenHidden": true,
    "isCurrent": true,
    "isMaster": true,
    "lastSeen": 1789968398982,
    "createdAt": 1789968398982
  },
  {
    "id": 7,
    "name": "My phone",
    "token": null,
    "tokenPreview": "aB3cD5eF",
    "tokenHidden": true,
    "isCurrent": false,
    "isMaster": false,
    "lastSeen": 1789968398982,
    "createdAt": 1789968398982
  }
]
```

| Field | Meaning |
|---|---|
| `token` | Always `null`. Get the full value from `POST /device/:id/reveal` |
| `tokenPreview` | 8-char fingerprint (same algorithm as the startup log: skip the `cz.` prefix, take 8 chars). Only for matching this row against other records |
| `tokenHidden` | Always `true`: clients should turn the "Copy" button into "Verify password to copy" |
| `isMaster` | Whether this row is the global master key (only a super-admin has one; it cannot be deleted) |

> Why every row is hidden now (since 2026-10-05 — previously only the master key was): a device
> token is a **long-lived credential**, and "already logged in" is not sufficient authorisation to
> see one. The device panel is far too easy to screenshot or glance at over someone's shoulder.
> The master key especially: once copied, changing your password does not help — a password change
> does not revoke the master key, so it keeps working until you rotate the master key itself.
>
> Two exceptions, both "generated on the spot, you would never get it otherwise":
> `POST /device` (create) and `POST /device/rotate` return the new token once;
> `POST /auth/login` hands the credential to the client by design.

### `POST /device/:id/reveal` logged in

Fetches the plaintext of **any** device token; **requires re-entering the password** (the password
of the currently logged-in account).

```json
// request
{"password": "password of the currently logged-in account"}

// response 200
{"token": "cz.xxxxxxxxxxxxxxxxxxxxxxxxxxxxxx"}
```

| Case | Response |
|---|---|
| Correct password | `200` + full token, plus a `device.reveal` audit entry |
| Wrong password | `403` "Password incorrect" (`success: false` in the audit). 🔴 **Must not be 401** — clients treat every 401 as "session expired" and bounce to the login page, even though the user is clearly still logged in |
| No `password` in the body | `400` "Enter your current password" |
| The row belongs to another user | `404` "Device not found" |

Rate limited to 30 / hour (`device_reveal`, keyed by **user**, not IP — the account is what is
being attacked). The password is compared in memory once; it never reaches the log or the audit
`meta`.

> Since 2026-10-05 **every** device row goes through this step (previously only the master key).
> The window was widened from 10/h to 30/h accordingly: someone with a few devices would burn
> through 10 requests quickly.

> If you write your own client, follow the same principle: **do not render the full token on
> screen** — that panel is often opened while screen-sharing, screenshotting or during remote
> support. The web UI renders only the fingerprint in the list; the full value goes straight to the
> clipboard via "Verify password to copy".

### `POST /device` logged in

```json
// request
{"name": "Tablet"}

// response
{"id": 5, "name": "Tablet", "token": "abc...", "createdAt": 1789...}
```

Defaults to "New device" when `name` is omitted.

### `DELETE /device/:id` logged in

- Deleting the current device → `400` "Cannot delete the device in use"
- Deleting the master-key row (`token === AUTH_TOKEN`) → `400` "This is the master key and cannot be deleted (to change it, replace AUTH_TOKEN itself)"
- Unknown id → `404` "Device not found"

```json
{"ok": true}
```

### `POST /device/rotate` logged in (limited to 20 / hour / IP)

Replaces **the token currently in use**. Because `DELETE /device/:id` refuses to delete the current
device, "one user = one login token" made a dedicated path mandatory — otherwise users could never
rotate a credential they are actively using.

- The old value **stops working immediately**; the new one is returned and the current session keeps
  working (no re-login)
- Other devices sharing that token get kicked and must log in again
- When logged in with the master key (`deviceId` is null) → `400` "The master key cannot be rotated here"

```json
{"ok": true, "token": "new full token"}
```

### `POST /user/avatar` logged in

Body is raw image bytes (≤ 5 MB); `png / jpg / gif / webp`, `svg` is rejected.

```bash
curl -X POST http://<host>:20010/user/avatar \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: image/png" \
  --data-binary @avatar.png
```

```json
{"ok": true, "avatar": "/user-avatars/user-2-1789.jpg"}
```

Uploading a new avatar deletes the old file and broadcasts `userUpdated` to all of that user's
connections (client and web UI both sync immediately, no manual refresh).

### `DELETE /user/avatar` logged in

```json
{"ok": true}
```

Also broadcasts `userUpdated`.

### `PATCH /user/profile` logged in

```json
// request
{"displayName": "Alice"}

// response
{"ok": true, "user": { "id": 2, "username": "alice", "displayName": "Alice", ... }}
```

The display name must be 1–32 chars after trimming, otherwise `400`.

### `PATCH /user/email` logged in

```json
// request
{"email": "alice@example.com"}     // or "" to clear

// response
{"ok": true, "user": { "id": 2, "username": "alice", "email": "alice@example.com", ... }}
```

- One email maps to at most one account (globally unique); duplicate → `409`
- Email is optional: send `""` to clear it; accounts without an email cannot use "forgot password"
- Invalid format → `400`

### `PATCH /user/username` logged in

Changes your **login username** (not the display name — that is `PATCH /user/profile`).

```json
// request
{"username": "yezi"}

// response
{"ok": true, "user": { "id": 1, "username": "yezi", "displayName": "yezi", ... }}
```

- Same rules as registration: 2–32 chars after trimming, only `a-z A-Z 0-9 _ - .`, else `400`
- **Globally unique**: colliding with someone else → `409` "Username already taken" (the check uses
  `AND id != ?`, so renaming back to your current name never trips it)
- New value identical to the old one (after trimming) → straight `200`, no DB write
- If a race slips past the pre-check, the `UNIQUE` constraint on `users.username` catches it and it
  still returns `409` rather than 500
- Rate limit: 10 / 10 min per IP

> **Changing the username breaks nothing**: permissions come from the `users.is_admin` flag and all
> authorisation goes by `user_id`; device tokens are bound to `user_id` too, and `auth.js` does
> `JOIN users` to read `username` live, so already-signed-in devices keep working. `migrate.js`
> likewise finds admins by `is_admin = 1` and no longer depends on the name `admin`.

### `PATCH /user/password` logged in

Change your own password (being logged in is the authentication, so the **old password is not
required**):

```json
// request
{"new_password": "newpassword123", "revokeDevices": false}

// response
{"ok": true, "revokedDevices": 0}
```

A super-admin resetting someone else (also without the old password):

```json
// request
{"userId": 2, "new_password": "newpassword123"}

// response
{"ok": true, "revokedDevices": 3}
```

The asymmetry is deliberate:

| Scenario | Needs `old_password`? | Devices |
|---|---|---|
| Changing your own | No (the session is the proof) | Signed-in devices are **kept** by default; pass `revokeDevices: true` to clear the others |
| Admin changing someone else | No | **All** of that user's devices are revoked by default (a password someone else could reset means the account is already unsafe) |

In every case **the device making the request is never cleared** — you cannot kick yourself offline.

Constraints: `new_password` 6–128 chars; it must differ from the current password (else `400`);
**non-super-admins** changing someone else get `403`. Rate limit 10 / 10 min per IP.

> ⚠️ Changing your own password no longer verifies the old one, which means **holding a device token
> is enough to change the password** — so every token in the device list is equivalent to a logged-in
> session. Guard them and delete unused devices.
>
> ⚠️ Logging in with the global `AUTH_TOKEN` (rather than a device token) leaves `deviceId` empty,
> so there is no way to identify "the current session" and everything gets cleared. The web UI uses
> a device token and is unaffected.

### `GET /user/list` super-admin

All users and their roles.

```json
[
  {
    "id": 1,
    "username": "admin",
    "displayName": "Admin",
    "avatar": null,
    "email": null,
    "isAdmin": true,
    "role": 2,
    "isSuper": true,
    "createdAt": 1789964364760
  }
]
```

### `PATCH /user/:id/role` super-admin

Promote / demote a user.

```json
// request
{"role": 1}

// response: the updated user object (same shape as above)
```

`role` must be `0` (ordinary user) / `1` (admin) / `2` (super-admin), otherwise `400`.

Two safeguards:

1. **You cannot change your own role** → `400`. One slip would otherwise demote you permanently.
2. **At least one super-admin must remain** → demoting the last super-admin returns `400`.

After the change, `userUpdated` is pushed to that user and the identity of their **already-online**
WebSocket connections is refreshed (see "role changes and live connections" below).

#### Permission boundary of the three roles

| Capability | Ordinary user | Admin (1) | Super-admin (2) |
|---|---|---|---|
| Channels they subscribe to | ✅ | ✅ | ✅ |
| Apps, routing rules | ✅ (own) | ✅ (own) | ✅ (own) |
| HTTPS certificates | ❌ | ❌ | ✅ |
| Audit log | ❌ | ❌ | ✅ |
| Edit / delete other people's channels | ❌ | ❌ | ✅ |
| Subscribe to other people's private channels | ❌ | ❌ | ✅ |
| Change other people's passwords | ❌ | ❌ | ✅ |
| **Read private channels they are not subscribed to** | ❌ | ❌ | ✅ |
| Promote / demote others | ❌ | ❌ | ✅ |

> ⚠️ **The old `isAdmin` flag changed meaning**: it now means `role >= 1`. If you have a script
> asserting "can see all channels" from `isAdmin`, that no longer holds — test `isSuper`
> (or `role === 2`) instead.
>
> ⚠️ **Role changes and live connections**: `ws.isAdmin` / `ws.isSuper` / `ws.subscribedChannels`
> are snapshots computed once when the connection is established. After a role change the server
> calls `refreshUserIdentity(id)` for all of that user's online connections, so promotion /
> demotion takes effect **immediately** without the other side reconnecting.


> ⚠️ Ordering is **ascending by `id`** (oldest first); paging uses `since = last id`, not `next`.
> Archived messages are **excluded by default** — pass `archived=all` to see them too.

### `GET /message/deleted` logged in

**Deletion tombstones.** Incremental sync with an id watermark (`since`) can only express
"something was added", never "something disappeared" — the server deletes id=50, the client has
already advanced to 100, and `WHERE id > 100` will never see it, leaving a ghost message that can
never be cleared. This endpoint returns "which ids were deleted", keyed by `deleted_at`.

| Param | Default | Meaning |
|---|---|---|
| since | 0 | Watermark: only tombstones with `deleted_at > since` (**milliseconds**, not an id) |
| sinceId | 0 | Secondary cursor: for rows with `deleted_at == since`, only take `id > sinceId` |
| limit | 500 | Page size, max 1000 |

Response:

```json
{
  "deleted": [
    {"id": 50, "channelId": 1, "deletedAt": 1789982996143},
    {"id": 51, "channelId": 1, "deletedAt": 1789982996143}
  ],
  "since": 0,
  "sinceId": 0,
  "next": {"since": 1789982996143, "sinceId": 51},
  "paging": {"size": 2, "limit": 500}
}
```

> ⚠️ **You must use the double cursor.** Deleting a channel or an app is **a single UPDATE with one
> shared `Date.now()`**, so the whole batch of tombstones carries an identical timestamp and `since`
> alone cannot express "how far into that one instant you got". Measured: 1200 same-instant
> tombstones yielded only 503 with a single cursor — **700 silently lost**.
>
> Usage: **pass the response's `next` back verbatim** (`since=next.since&sinceId=next.sinceId`); do
> not recompute it from the last row. `next` is `null` when you have reached the end. Clients should
> **persist both cursors** so an interruption mid-page does not lose the rest of that instant.
>
> Permissions match `GET /message`: admins see everything, ordinary users only see deletions in
> **channels they subscribe to** (otherwise ids from other channels would leak). With no
> subscriptions at all it returns an empty array.
>
> ⚠️ This endpoint depends on deleted rows **still existing** (soft delete only writes
> `deleted_at`). If "physically purge deleted rows" is ever implemented, every client must first be
> guaranteed to have caught up to the watermark.

### `POST /message` logged in

Request:

```json
{
  "title": "CPU alert",
  "message": "CPU 95%",
  "priority": 8,
  "channel_id": 1,
  "appid": 1,
  "tags": ["urgent"],
  "extras": {"image": "https://example.com/img.jpg"},
  "silent": false
}
```

Processing pipeline:

```text
1. Field clean-up (length truncation, priority clamped to 0-10)
2. Resolve the app: with no `appid`, take the **current user's own** first app (falls back to the
   global first app only if they own none)
   ⚠️ Ownership check: a logged-in user may only sign with **their own** app (super-admins exempt) —
      otherwise passing an arbitrary `appid` would let anyone impersonate someone else's app
      (ids are trivially guessable: 1, 2, 3…)
   → Resolve the channel: omitted means the app's default channel
   ⚠️ Delivery check: ordinary users must be a **subscriber** of that channel; super-admins are free
3. Run the routing engine applyRoutes — **only the current user's own rules** (see
   section 8, "rules are isolated per user")
   - may change priority, add tags, silence, forward, or drop
4. Write snapshots: `extras.sender` (sender) + `extras.app` (app, with name/icon, **no token**)
5. Try message aggregation
   - same channel + same app + same title + 5-minute window, and the original is not archived
   - ⚠️ also requires **the original's age < `AGG_MAX_LIFETIME_MS`** (default 30 min, `0` = unlimited) —
     the window measures "time since the last fold", and if that were the only condition an old
     message would be folded forever (rolling renewal): it would never float back to the top and it
     would push the earliest child out of `aggChildren`
   - on a hit, update the existing message's aggCount and aggChildren
   - on the **first fold**, the original message (#1) is itself prepended to `aggChildren`, and the
     image is stripped from the parent card:
     · only image-related keys are removed from `extras` — `image` / `client::display.url` /
       `client::notification.bigImageUrl` (`extras.sender` / `extras.app` are always kept; the
       parent card still shows the sender)
     · markdown images `![alt](url)` in the body are stripped too (**the two channels read images from
       different places**: the client reads `extras.image`, while the WebUI lifts the first image
       rendered from the body into the whole card's background)
     ⇒ an aggregated parent card shows only the title + `×N`, so it no longer misleads by showing
       the cover of "#1"; image and original text are preserved intact in the first child
6. Persist
7. Broadcast to the channel's subscribers
```

Response:

```json
// new message
{"id": 15, "appid": 1, "message": "CPU 95%", "title": "CPU alert", ...}

// dropped by a routing rule
{"dropped": true}

// folded into an existing message (returns the updated older message)
{"id": 14, "aggCount": 3, "aggChildren": [...], ...}
```

**Field limits when creating a message:**

| Field | Limit |
|---|---|
| `title` | truncated to 500 chars |
| `message` | truncated to 50000 chars |
| `extras` | if the serialized JSON exceeds 10000 chars the whole thing is dropped and set to `null` |
| `tags` | at most 20, each truncated to 50 chars |
| `priority` | clamped to 0–10, default 5 |

An app is the **sender identity** of a message. Each app has its own token, used for webhook

> 📌 **Apps are isolated per user** (since 2026-10-01): **every logged-in user** can manage their

> [`GET /admin/applications`](#15-super-admin-pages-site-wide-read-only).
> When creating/editing an app, `channel_id` must be a channel you subscribe to or created
> (super-admins exempt).

### `GET /application` logged in

```json
[
  {
    "id": 1,
    "name": "Default app",
    "description": "Self-hosted Gotify-compatible service",
    "image": null,
    "internal": false,
    "token": "aB3xK9mQ2p",
    "defaultPriority": 0,
    "channelId": 1,
    "template": null
  }
]
```

| Field | Meaning |
|---|---|
| token | The part used in the webhook URL. **10 chars of mixed-case letters + digits** (e.g. `aB3xK9mQ2p`), globally unique. Legacy 48-char hex values are converted automatically by the startup migration |
| channelId | Which channel the app sends to by default |
| template | Message template (JSON string), see [TEMPLATE.md](TEMPLATE.md) |
| internal | Always `false` (kept for Gotify client compatibility) |
| defaultPriority | Always `0` (same, not implemented) |

> 🔒 **This endpoint returns plaintext tokens.** Before 2026-09-30 it required only being logged in
> and ignored roles — and since registration is open, anyone could sign up and harvest every app's
> webhook credential. It was then tightened to `requireAdmin`, and since 2026-10-01 it is simply
> **filtered by `user_id`**, so each caller can only ever see their own apps and the leak surface is
> back to "the owner only".
>
> ⚠️ It once read `token: row.token || AUTH_TOKEN`, i.e. an empty token fell back to the **global
> master key**. The master key *is* super-admin identity (promote anyone, read every private
> channel), so a single row with an empty token would have handed over the whole instance. It is now
> `|| null` — better an invisible webhook URL than leaking the master key.

## 6. Attachments

Attachments are "store the file first, get a URL back"; how a message references it is up to the
caller. Images usually go into `extras.image`, other files go into a link in the body or into
`extras.attachment`.

### `POST /attachment?name=xxx.png` logged in

Body is **raw bytes** (≤ 20 MB); the filename comes from the query string.

```bash
curl -X POST "http://<host>:20010/attachment?name=shot.png" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: image/png" \
  --data-binary @shot.png
```

```json
{
  "url": "/attachments/9f3c1e...a7.png",
  "name": "shot.png",
  "size": 48213,
  "isImage": true,
  "contentType": "image/png"
}
```

| Field | Meaning |
|---|---|
| url | Direct static path, no auth required, safe for `<img src>` |
| name | Original filename (whitelist-sanitized and truncated to 120 chars; display only) |
| isImage | Whether magic-number detection says it is an image (svg excluded) |
| contentType | `image/png|jpeg|gif|webp` for images, else `null` |

> The on-disk filename is **16 random hex bytes** and unrelated to `name`, so URLs are unguessable.
> Dangerous extensions (`html / svg / js / xml …`) are forced to `.bin`, and the static handler sends
> `Content-Disposition: attachment` for anything that is not an image.

### Attachment reclamation

- Deleting a message: attachments **exclusively** owned by it are deleted too (kept if another
  undeleted message still references the same URL)
- At service start: the whole directory is scanned once and orphaned attachments nobody references
  are cleaned up

Clearing all messages, trimming history and deleting a channel do not notify attachments one by
one; the startup scan is the backstop.

## 7. Webhook

### `POST /hook/:token` public

`:token` is the **app object's `token` field**, not `AUTH_TOKEN`.

Four input modes:

**Mode 1: plain-text body (recommended)**

```bash
curl -d "the server is down" http://<host>:20010/hook/<app-token>
```

No `Content-Type` and no JSON needed. Chinese, spaces, newlines, emoji and Markdown can all be sent
directly.

**Mode 2: JSON body**

```bash
curl -X POST http://<host>:20010/hook/<app-token> \
  -H "Content-Type: application/json" \
  -d '{"title":"GitHub","message":"New commit","priority":5}'
```

| Field | Type | Meaning |
|---|---|---|
| message | string | Message body (required) |
| title | string | Title |
| priority | int | 0–10 |
| channel_id | int | Target channel |
| tags | string[] | Tags |
| extras | object | Arbitrary JSON |
| silent | bool | Silent |

**Mode 3: `multipart/form-data` form (`curl -F`)**

```bash
curl -F "title=Download finished" -F "message=Ubuntu 24.04.iso" -F "priority=5" \
  http://<host>:20010/hook/<app-token>
```

Programs like qBittorrent push with `-F`. Torrent names routinely contain spaces, quotes, percent
signs and brackets, which is easy to get wrong when hand-assembling JSON and naturally safe with
`-F`.

> ⚠️ In form mode **templates are not applied** (templates only render in JSON mode, i.e. when
> `_isJSON` is true). Form fields are converted with the same semantics as JSON: `priority` /
> `channel_id` are parsed as integers, `tags` is split on commas, `silent` accepts `true` and `1`.
> File contents are ignored.

**Mode 4: empty body + query parameters**

```bash
curl "http://<host>:20010/hook/<app-token>?message=hello&priority=5"
```

Typing it straight into a browser address bar works too.

### Query parameters

Applies to plain-text, form and JSON modes (**in JSON mode the body wins**):

| Param | Type | Meaning |
|---|---|---|
| message | string | Message body (used when the body is empty) |
| title | string | Title |
| priority | int | 0–10 |
| channel_id | int | Target channel |
| tags | string | Comma separated, e.g. `urgent,prod` |
| silent | bool | `true` or `1` triggers silent |

### Response and processing pipeline

HTTP responds **immediately**; the rest happens asynchronously inside `setImmediate`:

```json
{"received": true, "appid": 1}
```

```text
1. Find the app by token (not found → 404 unknown token)
2. Parse the body (JSON / form / plain text) and merge query parameters
3. If the app has a template and the body is JSON → render with the template engine
4. Otherwise → take message / title / priority / tags / extras directly
   - the title defaults to the app name, priority defaults to 5
5. createMessage() → routing → aggregation → persist → broadcast
   - routing **only runs the rules of the user who owns the app** (rules are per-user since
     2026-10-01)
   - on persist, `extras.app` is written (app snapshot: name/icon, no token)
```

If the final body is empty after trimming, the request is silently dropped and nothing is stored.

### Full examples

```bash
TOKEN=aB3xK9mQ2p

# minimal
curl -d "test" http://<host>:20010/hook/$TOKEN

# with title and priority
curl -d "CPU 95%" "http://<host>:20010/hook/$TOKEN?priority=9&title=urgent"

# specific channel
curl -d "deploy done" "http://<host>:20010/hook/$TOKEN?channel_id=2"

# with tags
curl -d "shipped" "http://<host>:20010/hook/$TOKEN?tags=deploy,prod"

# silent
curl -d "heartbeat" "http://<host>:20010/hook/$TOKEN?silent=true"

# Markdown
curl -d "**urgent** disk full" http://<host>:20010/hook/$TOKEN

# multi-line
curl -d "line one
line two" http://<host>:20010/hook/$TOKEN

# form (qBittorrent style)
curl -F "title=Download finished" -F "message=name with spaces.mkv" http://<host>:20010/hook/$TOKEN

# JSON (legacy usage)
curl -H "Content-Type: application/json" \
  -d '{"message":"JSON mode","priority":7}' \
  http://<host>:20010/hook/$TOKEN
```

## 8. Routing rules

The rule engine runs before a message is persisted. Rules are matched and executed in
`priority DESC` order.

> 📌 **Rules are isolated per user** (since 2026-10-01): **every logged-in user** can create their
> own rules, and they **only apply to their own messages** —
>   - a logged-in user sending a message → only their rules run
>   - a webhook → only the rules of the user who owns that app run
>
> Everyone sees only the rules they created (`user_id` = themselves); **admins cannot see other
> people's rules** — for a site-wide view use
> [`GET /admin/routes`](#15-super-admin-pages-site-wide-read-only).
>
> ⚠️ `broadcast_to` targets are filtered down to "public / you subscribe / you created"
> (super-admins exempt) — otherwise any registered user could push messages into someone else's
> private channel.

### `GET /route` logged in

```json
[
  {
    "id": 1,
    "name": "Urgent escalation",
    "enabled": true,
    "priority": 90,
    "conditions": {"priority_gte": 8},
    "actions": [{"type": "add_tag", "value": "urgent"}],
    "createdAt": 1789969060495
  }
]
```

### `POST /route` logged in

```json
// request
{
  "name": "Urgent escalation",
  "priority": 90,
  "enabled": true,
  "conditions": {"priority_gte": 8},
  "actions": [
    {"type": "set_priority", "value": 10},
    {"type": "add_tag", "value": "urgent"}
  ]
}
```

`priority` defaults to **50** and is clamped to 0–100. `conditions` and `actions` are required.

### `PATCH /route/:id` logged in

Any field can be changed (`priority` is clamped to 0–100 as well).

### `DELETE /route/:id` logged in

```json
{"ok": true}
```

### `POST /route/test` logged in

Tests whether a rule matches; nothing is modified.

```json
// request
{
  "conditions": {"priority_gte": 8},
  "actions": [{"type": "add_tag", "value": "urgent"}],
  "message": {"message": "hello", "priority": 9},
  "appName": "GitHub",
  "channelName": "Monitoring"
}

// response
{
  "matched": true,
  "dropped": false,
  "silent": false,
  "result": {"message": "hello", "title": "", "priority": 9, "tags": ["urgent"]},
  "extraChannels": []
}
```

| Field | Meaning |
|---|---|
| matched | Whether the conditions matched |
| dropped | Whether the message would be dropped |
| silent | Whether it would be silenced |
| result | The message after processing |
| extraChannels | List of forward target channels |

> `appName` / `channelName` take **names only** — the test context has no ids, so the `channel_id`
> and `app_id` conditions never match in this endpoint. To test those, send a real message and look
> at the result.

### `GET /route/templates` logged in

Returns 7 built-in templates (id, name, description, conditions, actions, priority).

Supported conditions and actions are documented in [ROUTES.md](ROUTES.md).

## 9. HTTPS certificates

Every endpoint in this section requires **super-admin**. Request bodies are raw PEM
(`express.raw`).

### `GET /certs/status` super-admin

```json
{
  "httpsEnabled": true,
  "hasCrt": true,
  "hasKey": true,
  "certInfo": {
    "valid": true,
    "certCount": 2,
    "subject": "CN=chatz.example.com",
    "issuer": "CN=R3, O=Let's Encrypt, C=US",
    "validFrom": "Sep  1 00:00:00 2026 GMT",
    "validTo": "Nov 30 23:59:59 2026 GMT",
    "expired": false,
    "notYetValid": false,
    "selfSigned": false,
    "hasChain": true
  },
  "keyInfo": {"valid": true, "type": "rsa", "bits": 2048},
  "keyMatch": true,
  "error": null
}
```

When `keyMatch` is `false`, `error` says the certificate and private key do not match.

### `POST /certs/fullchain` super-admin

```bash
curl -X POST http://<host>:20010/certs/fullchain \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/x-pem-file" \
  --data-binary @fullchain.pem
```

```json
{
  "ok": true,
  "certInfo": {"subject": "...", "issuer": "...", "validTo": "...", "certCount": 2, "hasChain": true},
  "httpsStarted": true,
  "message": "Certificate uploaded, HTTPS enabled"
}
```

Checks:

- Must contain a `BEGIN CERTIFICATE` block that parses
- **Expired / not yet valid** → `400`
- If a private key already exists, the **pairing** is verified first; mismatch → `400`

Uploading only one of the two files does not start HTTPS: it returns `httpsStarted: false` with
"waiting for private key / certificate".

### `POST /certs/privkey` super-admin

Same validation: key format plus pairing with the existing certificate.

### `DELETE /certs` super-admin

```json
{
  "ok": true,
  "message": "Certificate deleted",
  "httpsStopped": true,
  "note": "HTTPS service stopped"
}
```

`httpsStopped: false` means no HTTPS service was running at the time. Existing connections are
unaffected; **a container restart is required to fully shut it down**.

## 11. Audit log

### `GET /audit` super-admin

| Param | Default | Meaning |
|---|---|---|
| action | — | Filter by action, e.g. `login`, `register`, `app.delete` |
| userId | — | Filter by user |
| since | — | Only entries with `ts > since` |
| limit | 100 | Max 500 |

```json
[
  {
    "id": 42,
    "ts": 1789982992010,
    "userId": 1,
    "ip": "203.0.113.7",
    "action": "app.create",
    "target": "3",
    "meta": {"name": "GitHub"},
    "success": true
  }
]
```

Ordered `ts DESC` (newest first).

Recorded actions:

| action | Trigger | What `meta` holds |
|---|---|---|
| `register` | Registration success / failure | `isAdmin`, `reason` (failure reason) |
| `login` | Login success / failure | `reason` (`user not found` / `wrong password`) |
| `logout` | Logout (target = device id) | — |
| `auth.bad_token` | Called an endpoint with an invalid token | `method`, `path`, `tokenPrefix` (first 8 chars only) |
| `auth.forbidden` | Logged-in ordinary user hit an admin endpoint | `method`, `path` |
| `auth.forbidden_super` | Logged-in user hit a super-admin endpoint | `method`, `path`, `role` |
| `hook.bad_token` | Called a webhook with a nonexistent token | `tokenPrefix` (first 8 chars only) |
| `device.create` / `device.delete` | Issued / revoked a device token | `name` |
| `device.reveal` | Master key revealed after password re-check | `success` |
| `user.avatar.upload` / `user.avatar.delete` | Avatar | target = filename |
| `user.background.upload` / `user.background.delete` | Chat background | target = filename |
| `user.profile.update` | Display name changed | `displayName` |
| `user.email_change` | Email changed / cleared | `email` |
| `user.username_change` | Login username changed | `before`, `after`, `reason` (failure: duplicate) |
| `user.password_change` | Password changed / admin reset someone else's | `self`, `revokedDevices`, `reason` (failure reason) |
| `setup.complete` | First-run setup created the admin account | `username` |
| `config.set_lang` | Super-admin changed the instance-wide log language (`PUT /config/lang`) | `before`, `after`, `locked` |
| `app.create` / `app.update` / `app.delete` | App management | `name`, `changed` (which fields), `deletedMessages` |
| `app.icon.upload` | App icon | — |
| `channel.create` / `channel.update` / `channel.delete` | Channel management (incl. `is_public` flips) | `name`, `isPublic`, `changed`, `deletedMessages` |
| `channel.subscribe` / `channel.unsubscribe` | Subscribe / unsubscribe (= visibility of that channel's messages) | `name`, `private` |
| `channel.icon.upload` | Channel icon | — |
| `route.create` / `route.update` / `route.delete` | Routing rules (highest-privilege config) | `name`, `priority`, `actionTypes` |
| `certs.upload.crt` / `certs.upload.key` / `certs.delete` | TLS certificate / private key | `subject`, `validTo`, `type`, `bits`, `httpsStarted` |
| `message.create` | Sending a message with a login session (not the webhook path) | `appid`, `channelId`, `title`, `dropped`, `aggregated` |
| `message.delete` | Message deleted | `channelId`, `title`, `attachmentsRemoved` |
| `attachment.create` | Attachment uploaded | `name`, `size`, `ext` |

Throttling and redaction rules:

- `auth.bad_token` / `auth.forbidden` / `auth.forbidden_super` / `hook.bad_token` are failure events
  **an attacker can flood**, so they are capped at **one entry per 5 minutes** per IP (or per
  user + path) — otherwise one minute could push hundreds of thousands of rows and bury the real
  entries.
- Tokens are always truncated to the first 8 chars, and for certificates **only the type and bit
  size are recorded, never any PEM content** — the audit log is meant to be browsed in the web UI,
  not to become a second key store.
- `ip` is capped at 64 chars, `target` at 200, each `meta` value at 200, at most 20 fields.

Retention: by default `AUDIT_RETENTION_DAYS=90` days and at most `AUDIT_MAX_ROWS=50000` rows,
trimmed once at startup and then every 6 hours.

> The IP is the **TCP peer address** by default; `X-Forwarded-For` is trusted only when
> `TRUST_PROXY` is set (see the env-var table in README). Do **not** enable `TRUST_PROXY` when the
> port is exposed directly — that would let an attacker choose the IP used for rate limiting.

## 12. WebSocket

### Connecting

```text
ws://<host>:20010/stream?token=<token>
wss://<host>:20443/stream?token=<token>
```

An `Authorization: Bearer <token>` header works too.

Connection constraints:

- **The path must be `/stream`**; any other path is dropped during the upgrade
- Global connection cap **1000** → HTTP `503` when exceeded
- Per-user cap **10** → HTTP `429`
- Invalid token → HTTP `401`

### Server push

New message (no `event` field):

```json
{
  "id": 15,
  "appid": 1,
  "message": "CPU 95%",
  "title": "CPU alert",
  "priority": 8,
  "date": "2026-09-21T09:29:52.019Z",
  "extras": null,
  "channel_id": 1,
  "tags": ["urgent"],
  "aggCount": 1,
  "aggLastAt": 1789...
}
```

Events (carry an `event` field):

| event | Data | Trigger |
|---|---|---|
| `messageDeleted` | `{id}` | Message deleted |
| `messageAggregated` | `{message}` | Message folded into an existing card |
| `messageRead` | `{messageId, userId, readAt}` | Marked read |
| `messageUnread` | `{messageId, userId}` | Marked unread |
| `messagesReadAll` | `{channelId, readAt, count}` | Bulk read |
| `messageArchived` | `{messageId, archivedAt}` | Archived |
| `messageUnarchived` | `{messageId}` | Un-archived |
| `channelCreated` | `{channel}` | New channel (without subscribed/muted) |
| `channelUpdated` | `{channel}` | Channel modified |
| `channelDeleted` | `{channelId}` | Channel deleted |
| `subscriptionChanged` | `{channelId, action, muted?}` | You subscribed / unsubscribed / changed mute |
| `userUpdated` | `{}` | **Your own** account changed (avatar / display name / username / email / password) |

`subscriptionChanged` `action` values: `subscribed` / `unsubscribed` / `muted`.

> Channel metadata events (`channelCreated` / `channelUpdated` / `channelDeleted`) go to
> **"subscribers ∪ creator"** — super-admins **no longer** receive everything (since 2026-10-01, to
> save battery). A super-admin will not receive deletion events for channels they are not subscribed
> to, so a stale `subscribed=0` ghost row may linger locally (harmless); clients clean it up with the
> full reconciliation in `refreshChannelList` when the drawer opens or the app comes to the
> foreground.

#### `userUpdated`

Pushed only to **all connections of the user who was changed** (`broadcastToUser`); nobody else
receives it.

The payload is empty — it is only a "you should re-fetch" signal. On receipt, re-call
`GET /auth/me` and overwrite your local copy.

Why the new content is not inlined: every time the server added a field, every client would have to
be updated too, and missing one produces silent drift. Signal + re-fetch cannot drift.

Triggers: `POST/DELETE /user/avatar`, `PATCH /user/profile`, `PATCH /user/email`,
`PATCH /user/username`, `PATCH /user/password` (when an admin resets someone else, it is pushed to
that user).

Typical scenario: the phone client changes its avatar and the web UI shows it without a manual
refresh.

### Client → server

| Content | Purpose |
|---|---|
| `""` | Heartbeat (ignored by the server) |
| `"{}"` | Heartbeat (ignored by the server) |

### Per-channel delivery

| Identity | Receives |
|---|---|
| Any user | Messages of the channels **they subscribe to** |
| Legacy `AUTH_TOKEN` | Treated as its owning admin user — same subscription rule |

⚠️ Since 2026-10-01 there is **no admin/super-admin bypass** here either: message push
(`broadcastToChannel`) filters purely by `ws.subscribedChannels`. Super-admins see site-wide data
through [`GET /admin/*`](#15-super-admin-pages-site-wide-read-only), not through the stream.

A routing rule's `broadcast_to` can deliver one message to several channels; the server uses
`broadcastToChannels`, which **de-duplicates per client**, so you never receive the same message
twice.

### Heartbeat

The server sends `ping` every 30 seconds and the client must answer `pong`. The browser WebSocket
API handles this automatically; native clients must reply themselves.

Two consecutive unanswered pings (≈ 60 s) and the connection is `terminate`d.

## 14. Security response headers

Every response (static assets included) carries:

| Header | Value | Purpose |
|---|---|---|
| `Content-Security-Policy` | see below | Restricts where scripts / images / connections may come from — the last line of defence against XSS |
| `X-Content-Type-Options` | `nosniff` | Stops the browser from guessing MIME types (running `text/plain` as HTML) |
| `X-Frame-Options` | `DENY` | Blocks `<iframe>` embedding, prevents clickjacking |
| `Referrer-Policy` | `no-referrer` | No outbound Referer — `?token=` in the URL never leaks to a third party |
| `Permissions-Policy` | `geolocation=(), microphone=(), camera=(), payment=()` | Turns off unused device capabilities |
| `Strict-Transport-Security` | only over HTTPS and when `HSTS_MAX_AGE > 0` | Forces subsequent requests to HTTPS |

`X-Powered-By` is removed (Express is no longer advertised).

Current CSP value (`<Host>` is replaced with the request's Host header):

```text
default-src 'self';
script-src 'self' https://cdn.jsdelivr.net;
style-src 'self' 'unsafe-inline';
img-src 'self' data: blob: https: http:;
connect-src 'self' ws://<Host> wss://<Host>;
font-src 'self' data:;
media-src 'self' data: blob:;
object-src 'none';
frame-src 'none';
frame-ancestors 'none';
base-uri 'self';
form-action 'self'
```

Read this before changing any of it:

- **`script-src` deliberately omits `'unsafe-inline'`.** Adding it makes CSP essentially useless
  against XSS. The cost is that `index.html` cannot contain inline `<script>` — the splash transition
  and background pre-set live in `/boot.js` instead.
- **`style-src` must keep `'unsafe-inline'`**: the page uses `style="..."` attributes heavily and
  dropping it would break the whole layout. CSS injection is far less damaging than JS, so this is
  acceptable.
- **`connect-src` allows `ws://` / `wss://` for the request Host**: the page connects to
  `${proto}//${location.host}/stream`, whose scheme is `ws`, while CSP's `'self'` only covers
  same-scheme http/https — writing `'self'` alone would block realtime push.
- **`img-src` opens `https:` and `http:`**: cover images and markdown images can come from any
  external URL.
- **`script-src` allows `cdn.jsdelivr.net`**: the web UI's markdown renderer loads `marked` /
  `dompurify` from the CDN (pinned to `@3.0.6` / `@12.0.2`). If either fails to load it falls back to
  "escape and show as plain text", never to XSS. To drop this external dependency entirely, download
  both files into `public/` and reference them relatively.

HSTS is **off** by default (`HSTS_MAX_AGE=0`). Once sent, a browser remembers it and you cannot
take it back before it expires; self-hosted setups frequently swap certificates, change domains or
temporarily fall back to HTTP for debugging, and a browser would then **hard-refuse** the connection
in a way ordinary users cannot clear. It is therefore opt-in:

```bash
HSTS_MAX_AGE=15552000          # 180 days, a common value
HSTS_INCLUDE_SUBDOMAINS=true   # optional — only after confirming every subdomain supports HTTPS
```

> When HTTPS is terminated by a reverse proxy, `req.secure` comes from `X-Forwarded-Proto`, so you
> must also set `TRUST_PROXY` — otherwise HSTS is never sent.

## 15. Super-admin pages (site-wide, read-only)

Channels, apps and routing rules all became **per-user isolated** on 2026-10-01 — the everyday
endpoints (`GET /channel`, `GET /application`, `GET /route`) return only the caller's own, and
**admins cannot see other people's either**. To see who on the instance created what, a super-admin
uses this group.

> ⚠️ All of them require **super-admin** (role 2) and are **read-only**. The admin page currently
> only needs "visibility", so no create/update/delete is exposed — if manipulating other people's
> resources is ever needed it should get its own endpoints, so that each step can be audited
> individually, which is safer than one omnipotent PATCH.

### `GET /admin/channels` super-admin

```json
[
  {
    "id": 2,
    "name": "Family",
    "description": null,
    "image": null,
    "isPublic": true,
    "creatorId": 3,
    "creatorName": "bob",
    "createdAt": 1789...,
    "passwordProtected": false
  }
]
```

### `GET /admin/applications` super-admin

Carries `ownerId` / `ownerName`. ⚠️ `token` is **plaintext** — this is an admin page and a

```json
[{"id": 5, "name": "Tablet", "token": "abc...", "channelId": 1, "ownerId": 3, "ownerName": "bob", "createdAt": 1789...}]
```

Carries `ownerId` / `ownerName`; `conditions` / `actions` are already parsed into objects.

| aggCount | How many messages were folded in (≥ 1) |
| aggLastAt | Time of the last fold |
| aggChildren | Array of folded child messages (**includes the original itself**; the most recent 100 are kept. `AGG_MAX_LIFETIME_MS` prevents endless renewal from pushing early entries out) |

### Conventional fields inside `extras`

| Field | Meaning |
|---|---|
| `extras.image` | Cover image URL. Priority: `image` → `client::display.url` → `client::notification.bigImageUrl` |
| `extras.sender` | **Sender snapshot**, see below |
| `extras.app` | **App snapshot**, see below |

> **Should the image go in the body or in `extras`? Both.**
> The two channels read images from different places: the client (Android) reads `extras.image`,
> while the **WebUI reads the first image rendered from the body** (`public/app.js` lifts it into the
> whole card's background). Put it in only one place and the other side shows nothing.
>
> Conversely, `![](...)` inside the body is **stripped** in notification text, quoted summaries and
> aggregated children (the image is presented separately via `extras.image`, to avoid showing the
> same picture twice) — so do not rely on it as body content.

### Sender snapshot `extras.sender`

The message table has no `user_id` column, so sender info is written into `extras` as a snapshot:

```json
{
  "id": 2,
  "username": "alice",
  "displayName": "Alice",
  "isAdmin": false
}
```

- Present only for `POST /message` (there is an authenticated identity); **the webhook path has no
  logged-in user and omits the field**
- Written **after** the routing engine and **overwritten unconditionally** — otherwise any client
  holding a token could forge `sender` and impersonate someone
- Known cost: if the user later changes their display name, old messages still show the name as it
  was then

### App snapshot `extras.app`

Apps became **per-user isolated** on 2026-10-01 (`GET /application` returns only your own), so a
client can no longer look up the name/icon of "someone else's app" — yet people who subscribe to
someone else's channel **do see those messages**. So, exactly like `sender`, app info is written
into `extras` as a snapshot:

```json
{
  "id": 5,
  "name": "Jellyfin",
  "image": "/icons/5-1789.png"
}
```

- Written on **every** message (both the webhook and the `POST /message` paths)
- ⚠️ Contains only `id` / `name` / `image`, **never the token** (that is the webhook credential)
- `image` is a **relative path**; the client prepends its own server base URL
- Clients should **prefer it** over `GET /application` (that list now only has your own apps)
- Also written **after** the routing engine and **overwritten unconditionally**; known cost: renaming
  an app leaves old messages showing the name as it was then

## Full examples

### Complete curl walkthrough

```bash
HOST=http://localhost:20010

# 1. Register
curl -X POST $HOST/auth/register \
  -H "Content-Type: application/json" \
  -d '{"username":"alice","password":"alice123","displayName":"Alice"}'

# you get back: {"user":{...},"token":"cz.kR9mX2pQ7tL..."}
TOKEN="cz.xxxxxxxxxxxxxxxxxxxxxxxxxxxxxx"

# 2. List channels
curl $HOST/channel -H "Authorization: Bearer $TOKEN"

# 3. Create a channel
curl -X POST $HOST/channel \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"name":"Work","description":"Work notifications","is_public":true}'

# 4. Send a message
curl -X POST $HOST/message \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"title":"Test","message":"hello","priority":5,"channel_id":2}'

# 5. Pull the list
curl "$HOST/message?limit=50&since=0" -H "Authorization: Bearer $TOKEN"

# 6. Search
curl "$HOST/message/search?q=hello" -H "Authorization: Bearer $TOKEN"

# 7. Mark read
curl -X POST $HOST/message/15/read -H "Authorization: Bearer $TOKEN"

# 8. Archive
curl -X POST $HOST/message/15/archive -H "Authorization: Bearer $TOKEN"

# 9. Unread counts
curl $HOST/message/unread-counts -H "Authorization: Bearer $TOKEN"

# 10. App list
curl $HOST/application -H "Authorization: Bearer $TOKEN"
```

### Node.js WebSocket

```js
const WebSocket = require('ws');

const token = 'cz.xxxxxxxxxxxxxxxxxxxxxxxxxxxxxx';
const ws = new WebSocket('ws://localhost:20010/stream?token=' + token);

ws.on('open', () => console.log('connected'));

ws.on('message', (raw) => {
  const data = JSON.parse(raw.toString());

  if (data.id && data.message != null && !data.event) {
    console.log('new message:', data.title, '-', data.message);
    return;
  }

  switch (data.event) {
    case 'messageDeleted':
      console.log('deleted:', data.id);
      break;
    case 'messageAggregated':
      console.log('aggregated:', data.message.id, 'x' + data.message.aggCount);
      break;
    case 'messageRead':
      console.log('read:', data.messageId);
      break;
  }
});
```
